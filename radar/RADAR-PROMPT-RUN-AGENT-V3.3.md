# برومبت رادار — Run Android v3.3.0 «Run Agent» (جهة التطبيق فقط)

أنت تبني النسخة 3.3.0 من تطبيق Run Android انطلاقاً من سورس 3.2.0 المرفق (run-android-v3.2.0-source-for-agent.zip). هذه النسخة تضيف دعم «خدمة Run Agent» داخل التطبيق. اقرأ المهمة كاملة قبل أن تبدأ.

## طبيعة المشروع (اقرأ أولاً)
- تطبيق أندرويد **أصلي (Native) بلغة Java فقط** — 35 ملف .java، لا يوجد أي كود Kotlin في التطبيق (ملفات البناء فقط بصيغة Gradle Kotlin DSL: build.gradle.kts / settings.gradle.kts). لا Jetpack Compose — الواجهات XML Views كلاسيكية برمجياً وبالـXML.
- مشروع Gradle بموديول واحد (app)، applicationId = com.takidz.run، compileSdk 36، minSdk 24، targetSdk 34. البناء المرجعي: JDK 21 + Gradle 9.3.1 (GitHub Actions).
- المكتبات الأساسية الموجودة أصلاً: AndroidX AppCompat 1.6.1، Material 1.11.0، RecyclerView، ViewPager2، Eclipse Paho MQTT v3 1.2.5 (الشبكة/الغرف)، OkHttp 4.12.0، Gson 2.10.1 (تسلسل البروتوكول)، Glide 4.16.0 (الصور).
- البنية: network/MqttRoomManager.java يدير MQTT والغرف والحضور؛ models/ فيها Message/RoomData/OnlineUser وغيرها؛ utils/RoomCryptoUtils.java فيه توليد الأكواد وتسلسل البروتوكول؛ التخزين المحلي SharedPreferences باسم run_native_prefs_v1.
- اكتب كودك بـJava وبنفس أسلوب المشروع الحالي، وبنفس المكتبات — لا تُدخل لغة ولا مكتبة جديدة.

## ما هي خدمة Run Agent (السياق الكامل)
خدمة Run Agent = غرفة Run خاصة يكون فيها وكيل ذكاء اصطناعي (اسمه «موس») عضواً دائماً عبر جسر برمجي يعمل في بيئة الوكيل على مدار الساعة: صاحب التطبيق يرسل رسالة في الغرفة من التطبيق العادي، الجسر يوقظ الوكيل، والوكيل يرد بنشر رسالة في نفس الغرفة بنفس البروتوكول الحالي.
- **مهمتك أنت: جهة التطبيق فقط.** الجسر نفسه يبنيه موس في بيئته — لا تبنِ أي خادم أو شيطان (daemon) أو كود شبكة جديد.
- الوكيل عندك مجرد عضو عادي في غرفة عادية بنفس البروتوكول الحالي 100%. كل ما تبنيه هو: تثبيت هذه الغرفة وتجربتها كغرفة وكيل + أسطح واجهة لميزات موجودة أصلاً في البروتوكول.

## قواعد لا تُكسر
1. ابْنِ على سورس 3.2.0 المرفق كما هو. حافظ على: كل الميزات الحالية، الثيمات السبع (بما فيها Glass والوضع الداكن لكل تصميم)، البروتوكول والمواضيع (runapp/v1/…)، طبقة RoomCryptoUtils، مفاتيح التخزين (run_native_prefs_v1)، وملف debug.keystore في جذر المشروع — لا تمسّه ولا تستبدله ولا تحذفه (توقيع دائم؛ كسره = كسر التحديثات).
2. لا مواضيع MQTT جديدة، لا بروتوكول جديد، لا مكتبات جديدة ثقيلة. كل ما تحتاجه موجود في الكود الحالي.
3. التصميم: لغة 3.2 الحالية المطابقة لتصميم A — لا إعادة تصميم. أي سطح جديد يتبع نفس البطاقات والمسافات والألوان، ويعمل في الثيمات السبع كلها وبالعربية RTL كاملة.
4. versionCode = 6، versionName = "3.3.0".
5. لا تبنِ APK ولا تدّعِ اختباراً على جهاز. أعد السورس كاملاً ZIP + ملاحظات تنفيذ صادقة (IMPLEMENTATION-NOTES) تذكر كل ملف غيّرته ولماذا، وأي شيء لم تستطع إتمامه بصراحة.

## ما تبنيه (جهة التطبيق)
### 1) غرفة الوكيل المثبتة
- إعداد جديد «غرفة Run Agent»: المستخدم يلصق كود غرفة مرة واحدة (أو ينشئ غرفة جديدة ويأخذ كودها) فتُحفظ في التفضيلات كمفتاح agent_room_code.
- الغرفة المحفوظة تظهر مثبّتة دائماً في أعلى قائمة الغرف/الرئيسية ببطاقة خاصة: أفاتار الوكيل، اسم «Run Agent — موس»، وحالة حضوره الحقيقية (النقطة 2). الضغط عليها يدخل الغرفة مباشرة.
- إن لم يُضبط كود، تظهر البطاقة كدعوة ضبط («اربط غرفة الوكيل») تفتح حوار اللصق/الإنشاء.

### 2) حضور صادق للوكيل
- حالة الوكيل تُشتق من موضوع حضور الغرفة (room/<code>/presence/<agentUserId>) وقائمة أعضاء الغرفة الحالية: نبضة حديثة = «متصل»؛ نبضة قديمة/غائبة = «غير متاح حالياً» بنص رمادي هادئ. لا حالة «متصل» تجميلية كاذبة أبداً.
- معرّف الوكيل ثابت ويُعرّف في كودك كقائمة معرّفات وكيل معروفة (agent userId prefix «agent-») حتى تميّزه الواجهة عن الأعضاء العاديين دون أي تغيير بروتوكول.

### 3) مذكرة الغرفة المشتركة (سطح بارز)
- داخل غرفة الوكيل، زر/بطاقة «المذكرة المشتركة» في الأعلى تفتح محرر حقل Note الموجود أصلاً في RoomData: قراءة وتحرير وحفظ (يعيد نشر حالة الغرفة كالمعتاد). هي ذاكرة مشتركة بين المستخدم والوكيل — اجعل الوصول إليها من غرفة الوكيل أسرع من أي غرفة عادية.

### 4) الرسائل الصوتية من الوكيل
- تأكد أن الرسائل الصوتية الواردة (type=voice) تُعرض بمشغّل كامل داخل غرفة الوكيل، وأي نص مرفق معها (caption) يظهر كنص تحت المشغّل مباشرة («النص المرفق»). لا تكسر عرض الصوتيات في الغرف العادية.

### 5) إيصالات صادقة داخل غرفة الوكيل فقط
- باستعمال حقلي deliveredTo/readBy الموجودين أصلاً في Message: في غرفة الوكيل، رسائل المستخدم تعرض تسمية حالة صغيرة: «وصلت إلى الجسر» عند وجود معرّف الوكيل في deliveredTo، و«قرأها موس» عند وجوده في readBy. في الغرف العادية يبقى سلوك الإيصالات الحالي كما هو دون تغيير.

### 6) مؤشر كتابة الوكيل
- تأكد أن مؤشر «يكتب الآن…» (موضوع /typing الحالي) يعمل عندما يكون الكاتب هو الوكيل، ويعرض «موس يكتب…» داخل غرفة الوكيل.

### 7) أزرار أوامر سريعة في غرفة الوكيل
- شريط رقائق (chips) فوق صندوق الإدخال داخل غرفة الوكيل فقط، كل رقاقة تُدرج نصاً في صندوق الإدخال (لا ترسل مباشرة):
  - «الحالة» ← ‎/حالة
  - «كتم ساعة» ← ‎/كتم 1h
  - «رد بصوتك» ← «رد بصوتك: »
  - «طلب إصلاح» ← «طلب إصلاح: » (قالب Live تعديل: المستخدم يكمل وصف المشكلة بعد النقطتين)
- الرقائق تتبع ثيم الغرفة الحالي وتختفي في الغرف العادية.

### 8) روابط/ملفات APK داخل الغرفة
- تأكد أن مرفقات الملفات وروابط APK الواردة في غرفة الوكيل تُفتح/تُثبّت عبر مسار التعامل مع الملفات الحالي دون كسر (هذا مسار تسليم Live تعديل). لا تبنِ مثبّتاً جديداً.

## ما لا تبنيه
- لا جسر، لا خادم، لا استماع خلفي عندك، لا حسابات، لا ربط صلاحيات، لا أي تغيير في MqttRoomManager منطقياً عدا ما يلزم لعرض الحضور/الإيصالات أعلاه قراءةً فقط إن أمكن.

## التسليم
ZIP السورس الكامل المعدّل + IMPLEMENTATION-NOTES صادقة: قائمة الملفات المعدّلة، كيف اختبرت منطقياً (قراءة/محاكاة ذهنية للمسارات)، وأي قصور. تذكير: debug.keystore يجب أن يعود في الـZIP بايتاً ببايت كما استلمته.
